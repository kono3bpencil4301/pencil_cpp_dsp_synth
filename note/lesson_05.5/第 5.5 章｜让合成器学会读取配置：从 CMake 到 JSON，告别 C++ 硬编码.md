# 第 5.5 章｜让合成器学会读取配置：从 CMake 到 JSON，告别 C++ 硬编码

> MiniAudioDSP Lab · 工程化插曲
>
> 本章环境以 **Windows + MSYS2 UCRT64 + GCC + Ninja + CMake** 为主；附录介绍 **vcpkg + MSVC**。代码沿用第五章的 `Voice`、`PolySynth`、`WriteWavHeader()` 和 `WriteU16LE()` 接口。本文讨论的是**离线合成并导出 WAV**，不是实时音频热更新。

在上一期节目当中，我们终于让 C++ 学会了演奏多个音符。通过 PolySynth，每个音符都获得了自己的 Voice、Oscillator 和 ADSR 状态。只要把 C4、E4、G4 交给合成器，我们就能输出一个 C Major 和弦；再错开各自的起音时间，和弦又能变成琶音。

但是，当我想把刚才的锯齿波换成正弦波，或者把 Attack 从 0.05 秒改成 0.5 秒时，突然发现了一个很尴尬的问题：**我每调一次音色，都要重新打开 `main.cpp`，改几个数字，再重新编译一次。**

如果把这一切放在音乐制作软件中，情况就更离谱了。假设你在合成器面板上把 Attack 旋钮往右转了一点，软件却提示：

> 参数修改成功！请重新编译整个合成器。

这听起来可不像一件成熟的电子乐器应该做的事情。

所以第 5.5 章先不急着做滤波器。我们需要给前五章已经实现的声音系统做一次小型工程化改造：**让声音算法继续待在 C++ 中，把用户希望反复修改的参数搬到 JSON 文件里。**

这一章的目标是：读者不需要更改或重新编译声音算法，只需要修改一份 `config.json`，重新运行离线程序，就能听到不同的波形、ADSR 包络与音符编排；与此同时，我们还要避免把一大堆 JSON 读取逻辑全部塞进 `main()`。

## 一、为什么我们需要配置文件？

先回顾第五章的 Voice 初始化代码：

```cpp
voice.setWavetable(OscillatorType::Sawtooth);
voice.setSampleRate(44100.0);
voice.setCurveType(CurveType::Linear);
voice.setADSRAll(0.05f, 0.3f, 0.3f, 1.5f);
```

这四行代码都没有问题。但如果它们被写死在程序里，我们每次尝试一个新音色，都在做两件其实不应该绑在一起的事：

1. **修改算法或程序结构**，比如增加一种真正的新振荡器、修复包络状态机，这通常需要修改 C++ 并重新编译。
2. **修改算法已经支持的参数**，比如选择 Sawtooth、设置 Sustain Level，这不应该要求修改源代码。

前者属于 *Code*，后者属于 *Configuration*。把它们区分开，是本章的核心：**Separation of Configuration and Code（配置与代码分离）**。

当然，JSON 并不能凭空发明新的 DSP 算法。假如我们的 `OscillatorType` 只实现了 Sine、Square、Sawtooth 和 Triangle，那么在 JSON 中输入 `supersaw` 并不会自动生成 Supersaw。JSON 只能选择**代码已经实现**的能力。

### 一个具体对比

原本的硬编码：

```cpp
voice.setWavetable(OscillatorType::Sawtooth);
voice.setCurveType(CurveType::Linear);
```

配置驱动后的文件：

```json
{
    "wavetable": "sine",
    "curveType": "EaseOut"
}
```

我们的 C++ 不再写死 `Sawtooth` 或 `Linear`，而是在运行时读取配置文件，再把字符串转换成合成器能理解的类型。

这样能带来三个直接好处。首先是**修改快**：不需要重新编译已有程序。其次是**可复现**：保存一份配置，就相当于保存了一次离线合成的声音设定。最后是**更容易扩展**：以后做 Preset、GUI 参数面板和工程文件保存时，都有一套现成的数据入口。

但也要提醒一下：修改 JSON **不会自动更新已经打开、正在运行的合成器对象**。本章是在程序启动时读取配置，随后生成 WAV。未来如果想实现“边转旋钮边听声音”，还需要处理运行时参数更新和实时音频线程安全问题。

## 二、CMake：先把工程管理好

在前几期教程里，我们更关心“如何生成声音”。但工程文件越来越多后，声音模块逐渐被拆成 `Voice`、`PolySynth`、`Envelope`、`Oscillator`、WAV 写入模块等，手动敲一长串 `g++` 命令并不是好办法。

CMake 是一种**构建系统生成工具**。它读取 `CMakeLists.txt`，根据你选择的工具链和生成器，生成 Ninja、Make 或 Visual Studio 等工具能够使用的构建规则。**CMake 本身不是编译器**；最后真正编译 `.cpp` 的，仍然是 GCC、Clang 或 MSVC。

本章以我当前使用的 MSYS2 UCRT64 为例：

```text
CMakeLists.txt
      │
      ▼
    CMake  ── 查找依赖、配置编译规则
      │
      ▼
    Ninja  ── 决定哪些文件需要构建
      │
      ▼
 GCC / G++ ── 编译 C++ 源代码
      │
      ▼
  可执行程序
```

### 2.1 安装 MSYS2 UCRT64 工具

在 Windows 中打开 **MSYS2 UCRT64** 终端。不要把 MSYS、MINGW64、UCRT64 三种环境混为一谈：它们的工具路径与二进制目标可能不同。首先根据 MSYS2 的提示完成系统更新：

```bash
pacman -Syu
```

某些更新过程可能要求关闭窗口，重新打开 MSYS2 UCRT64 后继续更新。随后安装开发工具和 JSON 库：

```bash
pacman -S --needed \
    mingw-w64-ucrt-x86_64-gcc \
    mingw-w64-ucrt-x86_64-cmake \
    mingw-w64-ucrt-x86_64-ninja \
    mingw-w64-ucrt-x86_64-nlohmann-json
```

其中：

- `gcc` 提供 C/C++ 编译工具；
- `cmake` 负责工程配置；
- `ninja` 是构建执行工具；
- `nlohmann-json` 是本章的 JSON 解析库。

可以检查：

```bash
which cmake
which g++
which ninja

cmake --version
g++ --version
```

在 UCRT64 终端中，我们期望它们主要来自 `/ucrt64/bin/`。如果终端实际调用了另一套编译器，那么接下来即使 JSON 安装成功，也可能出现 CMake 找不到包的情况。

### 2.2 为什么安装了 nlohmann-json，CMake 还是找不到？

我在搭建这一章时，就遇到过这样的报错：

```text
Could not find a package configuration file provided by "nlohmann_json"
with any of the following names:

    nlohmann_jsonConfig.cmake
    nlohmann_json-config.cmake
```

它不是在说 JSON 语法有错，而是在说 **CMake 不知道从哪里找到这个第三方库的包配置文件**。

对于 MSYS2 UCRT64，安装后的相关文件一般位于：

```text
C:/msys64/ucrt64/
├── include/nlohmann/json.hpp
└── share/cmake/nlohmann_json/nlohmann_jsonConfig.cmake
```

文件存在，并不代表 CMake 就一定使用了正确的搜索路径。这里可以用安装前缀来告诉它：

```bash
cmake -S . -B cmake-build-ucrt -G Ninja -DCMAKE_PREFIX_PATH=/ucrt64
```

其中：

- `-S .` 表示当前目录是源码目录；
- `-B cmake-build` 表示将构建文件放进这个目录；
- `-G Ninja` 表示让 CMake 生成 Ninja 构建规则；
- `-DCMAKE_PREFIX_PATH=/ucrt64` 表示额外从 UCRT64 前缀搜索依赖。

如果你已经用错误配置生成过 `cmake-build`，建议改用新目录，而不是一直复用缓存。CMake 会把编译器与依赖查找结果缓存到 `CMakeCache.txt` 里，导致“明明安装好了却还找不到”的情况持续存在。

**请注意：** 上面的命令只是正确配置该工具链的一条常见路径，并不能保证消除项目里其他 CMake 指令造成的停顿。如果 CMake 在 `Detecting CXX compile features - done` 后没有继续输出，不代表一定卡在 JSON。应该检查 `CMakeLists.txt` 中后续的 `find_package()`、`FetchContent` 和自定义命令，而不是贸然重装 GCC。

排查时可以执行：

```bash
cmake -S . -B cmake-debug -G Ninja \
    -DCMAKE_PREFIX_PATH=/ucrt64 \
    --trace-source=CMakeLists.txt \
    --debug-find-pkg=nlohmann_json
```

### 2.3 CMakeLists.txt 怎样写？

假设我们的工程按下面的目录组织：

```text
pencil_mini_audio_lab/main/
├── CMakeLists.txt
├── config/
│   └── config.json            # 第一次运行时生成
├── src/
│   ├── main.cpp
│   ├── config_manager.h       # 本章新增
│   ├── config_manager.cpp     # 本章新增
│   ├── synth_renderer.h       # 本章新增
│   ├── synth_renderer.cpp     # 本章新增
│   ├── voice.h / voice.cpp    # 以前章节已有
│   ├── poly_synth.h / poly_synth.cpp
│   └── wav_and_pcm.h / wav_and_pcm.cpp
└── cmake-build/          # 自动生成，不建议提交仓库
```

上面的文件位置只是一个教学示例。如果你此前将头文件放在 `include/`，或将实现文件放在其他目录，记得相应修改 CMake 中的源文件路径。

我们的 CMake 配置可以写为：

```cmake
cmake_minimum_required(VERSION 3.20)
project(MiniAudioDSP_Lab LANGUAGES CXX)

set(CMAKE_CXX_STANDARD 20)
set(CMAKE_CXX_STANDARD_REQUIRED ON)
set(CMAKE_CXX_EXTENSIONS OFF)

find_package(nlohmann_json CONFIG REQUIRED)

add_executable(mini_audio_demo
    src/main.cpp
    src/config_manager.cpp
    src/synth_renderer.cpp

    # 按你自己的工程结构填写现有 DSP 源文件
    src/voice.cpp
    src/poly_synth.cpp
    src/wav_and_pcm.cpp

    # 如果 Oscillator / Envelope 另有 .cpp，继续加入
)

target_include_directories(mini_audio_demo PRIVATE
    "${CMAKE_CURRENT_SOURCE_DIR}/src"
)

target_link_libraries(mini_audio_demo PRIVATE
    nlohmann_json::nlohmann_json
)
```

这里最重要的两行，是：

```cmake
find_package(nlohmann_json CONFIG REQUIRED)

target_link_libraries(mini_audio_demo PRIVATE
    nlohmann_json::nlohmann_json
)
```

`find_package()` 负责找到安装包提供的 CMake 配置，`target_link_libraries()` 在这里则把 JSON 库的使用要求传给可执行目标，例如头文件搜索路径。**虽然 `nlohmann/json` 是 Header-only（纯头文件）库，通常不需要链接额外的二进制 JSON 库，但 CMake 的目标依赖仍然很有用。**

现在可以配置并构建：

```bash
cd /d/Dev/CPP/pencil_mini_audio_lab/main
cmake -S . -B cmake-build -G Ninja -DCMAKE_PREFIX_PATH=/ucrt64
cmake --build cmake-build
```

到这里，我们已经为 JSON 准备好了入口。不过库安装成功，还不代表我们理解了 JSON。接下来先从最基础的文件读写讲起。

## 三、什么是 JSON？为什么它适合合成器？

JSON 全称 **JavaScript Object Notation**，是一种文本数据交换格式。它虽然诞生于 JavaScript 生态，但如今 C++、Python、Java、JavaScript 等语言都可以读写它。

我们先看一个小例子：

```json
{
    "wavetable": "sawtooth",
    "curveType": "linear",
    "ADSR_config": [0.05, 0.3, 0.3, 1.5]
}
```

它并不是什么特别玄妙的东西，简单理解就是一张描述参数的表。

JSON 常用的几种数据类型包括：对象 `{}`、数组 `[]`、字符串、数字、布尔值和 `null`。在合成器里，不同数据各有用途。比如 `wavetable` 用字符串表示振荡器类型，`ADSR_config` 用数组保存四个参数，多个音符则放在 `noteNumber` 数组里。

读者要注意两个很容易踩坑的区别：

```json
{
    "voiceCount": 3,
    "noteNumber": [60, 64, 67]
}
```

`voiceCount` 是一个单独的整数，而 `noteNumber` 是包含三个整数的数组。在 C++ 中读它们时，操作当然不同。

JSON 还有一条规则：**标准 JSON 不支持注释**。不要在 `config.json` 里直接写 `// 我喜欢锯齿波`，否则标准解析器可能会报错。我们可以在教程正文里解释字段含义，而不要把注释塞进运行时配置。

### 3.1 让 C++ 创建 JSON 文件

先写一个独立的小实验，暂时不涉及合成器：

```cpp
#include <fstream>
#include <iostream>
#include <nlohmann/json.hpp>

using json = nlohmann::json;

int main()
{
    json config;
    config["wavetable"] = "sawtooth";
    config["curveType"] = "linear";
    config["ADSR_config"] = {0.05, 0.3, 0.3, 1.5};

    std::ofstream output("demo.json");
    if (!output)
        return 1;

    output << config.dump(4) << '\n';
    std::cout << "JSON created\n";
}
```

`json config;` 创建一个 JSON 值，`config["wavetable"]` 通过键名赋值，`dump(4)` 将内存中的 JSON 转成带四空格缩进的文本，而 `std::ofstream` 负责写进文件。

它生成的 `demo.json` 会出现在**程序运行时的当前工作目录**中，而不是必然出现在 `main.cpp` 所在文件夹。这个区别在使用 IDE、Ninja 和 CMake 时非常重要。

### 3.2 读取并修改已有 JSON

如果已经有 `demo.json`，我们可以读取、修改，再保存：

```cpp
std::ifstream input("demo.json");
if (!input)
    throw std::runtime_error("Cannot open demo.json");

json config;
input >> config; // 反序列化：文本 -> JSON 对象
input.close();

config["wavetable"] = "sine";
config["ADSR_config"][0] = 0.5; // Attack 改为 0.5 秒

std::ofstream output("demo.json");
if (!output)
    throw std::runtime_error("Cannot write demo.json");

output << config.dump(4) << '\n'; // 序列化并写回磁盘
```

请把这两个动作分清楚：`config[...] = ...` 只是**修改内存中的数据**，`output << config.dump(4)` 才是**把修改写回磁盘**。

但对于合成器而言，我们通常**不需要在 C++ 里反复改写 JSON**。更符合本章目的的工作方式，是用户先打开 JSON 文本文件修改参数，C++ 启动时**读取它**，最后生成新的音频。

## 四、把第五章的和弦与琶音搬进 JSON

在第五章，我们的代码这样写：

```cpp
std::vector<int> noteNums = {60, 64, 67};
std::vector<float> velocities = {0.8f, 0.7f, 0.6f};
std::vector<float> holdTimes = {2.0f, 2.0f, 2.0f};
std::vector<float> startTimes = {0.0f, 0.0f, 0.0f};
```

它已经可以驱动 PolySynth，不过音符变动仍然需要改源码。接下来让配置文件承担同样的工作，同时保留第五章正在使用的字段名称，减少迁移成本。

我们采用下面这份 `config/config.json`：

```json
{
    "poly_chord": {
        "note": {
            "noteNumber": [60, 64, 67],
            "noteVelocity": [0.8, 0.7, 0.6],
            "holdTimes": [3.0, 3.0, 3.0],
            "startTime": [0.0, 0.0, 0.0]
        },
        "ADSR_config": [0.05, 0.3, 0.3, 1.5],
        "wavetable": "sawtooth",
        "curveType": "linear"
    },
    "poly_arpeggio": {
        "note": {
            "noteNumber": [60, 64, 67, 72],
            "noteVelocity": [0.8, 0.7, 0.6, 0.5],
            "holdTimes": [2.0, 2.0, 2.0, 2.0],
            "startTime": [0.0, 0.8, 1.6, 2.4]
        },
        "ADSR_config": [0.05, 0.3, 0.3, 1.5],
        "wavetable": "sine",
        "curveType": "linear"
    }
}
```

这里的 `poly_chord` 与 `poly_arpeggio` 是两条音轨的名字，分别准备生成 `poly_chord.wav` 和 `poly_arpeggio.wav`。如果未来再增加 `poly_melody`，程序也应该能够自动找到它。

特别解释几个字段：

| 字段 | 含义 | 示例 |
| --- | --- | --- |
| `noteNumber` | MIDI 音符序号 | `60` 为 C4 |
| `noteVelocity` | 音符力度，本教程约定为 0～1 | `0.8` |
| `holdTimes` | 从 NoteOn 到 NoteOff 的持音时间，单位秒 | `3.0` |
| `startTime` | 音符在全局时间轴上的起始时间，单位秒 | `0.8` |
| `ADSR_config[0]` | Attack 时间，秒 | `0.05` |
| `ADSR_config[1]` | Decay 时间，秒 | `0.3` |
| `ADSR_config[2]` | Sustain 电平，不是时间 | `0.3` |
| `ADSR_config[3]` | Release 时间，秒 | `1.5` |
| `wavetable` | 本教程沿用的波形选择字段 | `sine`、`sawtooth` |
| `curveType` | 当前 Voice 接口支持的统一包络曲线类型 | `linear`、`EaseIn`、`EaseOut` |

之前我们在 ADSR 篇专门强调过：Sustain 是音量电平而不是时长。因此读 JSON 时，虽然四个值放在一个数组里，也不要把四个参数都当成“秒”。

此外，之前的 JSON 还有一个 `voiceCount` 字段。这里我选择**不再要求用户单独维护它**。既然 `noteNumber` 已经有三个元素，那么 Voice 数量完全可以由 `noteNumber.size()` 推导。否则用户新增第四个音符，却忘记把 `voiceCount` 从 3 改成 4，就会制造出两份彼此矛盾的数据。

**要牢记：数组长度只是合成器需要分配 Voice 数量的依据；它不会自动解决真实实时合成器中 Voice Allocation 的复杂问题。** 我们仍然采用第五章的“离线渲染前预先创建 Voice”的设计。

## 五、从 JSON 数组读成 std::vector

这是我们最先应该掌握的技巧：不需要先写一个循环，逐个把 JSON 数据 `push_back()` 到另一个数组。`nlohmann/json` 已经允许直接转换：

```cpp
const auto &note = config.at("poly_chord").at("note");

std::vector<int> noteNums =
    note.at("noteNumber").get<std::vector<int>>();

std::vector<float> velocities =
    note.at("noteVelocity").get<std::vector<float>>();

std::vector<float> holdTimes =
    note.at("holdTimes").get<std::vector<float>>();

std::vector<float> startTimes =
    note.at("startTime").get<std::vector<float>>();
```

`at()` 负责按照指定键名查找配置；如果键不存在，它会抛出异常，而不是默默创建一个新字段。`get<std::vector<int>>()` 则完成 JSON 数组到 C++ 动态数组的类型转换。

不过，既然 JSON 允许用户编辑，我们还得做检查。比如音高数组有 4 个元素，力度数组却只有 3 个，如果直接按索引访问，就可能越界。

```cpp
if (noteNums.size() != velocities.size() ||
    noteNums.size() != holdTimes.size() ||
    noteNums.size() != startTimes.size())
{
    throw std::runtime_error("Note parameter array lengths do not match");
}
```

如果只是为了读取 JSON，请不要写出下面这样的代码：

```cpp
// 错误：push_back() 返回 void，它负责追加数据，不返回 vector
std::vector<int> noteNums = note["noteNumber"].push_back(60);
```

`push_back()` 是修改容器的操作。我们的目标是**读取已有数组**，而不是把读取到的元素再次塞回 JSON。更何况上面的错误写法还会触发 `void` 不能转换成 `std::vector<int>` 的编译错误。

到这里，我们已经可以实现最基本的 JSON 数据访问。但下一步就来了一个工程问题：**这些读取语句应该放在哪里？**

## 六、为什么不能把所有解析代码都塞进 main()？

最直接的写法当然是：在 `main()` 打开 JSON，读取音符，初始化 Voice，调用 PolySynth，输出 WAV。代码量不多时，似乎也没什么问题。

可等我们继续增加 Filter、LFO、FM、MIDI 后，`main()` 就会越来越庞大。更麻烦的是，声音算法里到处出现 `config["poly_chord"]["ADSR_config"][0]`，这意味着 DSP 类需要知道外部配置文件怎么组织。

假如将来把 `ADSR_config` 改名为 `envelope`，难道我们还要跑遍所有 DSP 类，把 JSON 键名逐一修改吗？

因此我们引入一个新模块：**ConfigManager（配置管理器）**。

我希望声音系统看到的并不是 JSON 语法，而是已经转换好的 C++ 数据结构：

```text
                 config.json
                     │
                     ▼
                ConfigManager
          （创建 / 读取 / 校验 / 解析）
                     │
                     ▼
               TrackConfig
      （C++ 结构体，不依赖 JSON 语法）
                     │
                     ▼
               SynthRenderer
         （类型转换 / Voice 配置 / 生成）
                     │
                     ▼
                PolySynth
                     │
                     ▼
              Float Buffer
                     │
                     ▼
                 WAV File
```

这种分层并不是为了“多创建几个文件显得专业”。它的真正好处在于：**配置文件怎么存，是 ConfigManager 的工作；声音怎么合成，是 SynthRenderer 和 DSP 模块的工作。**

现在我们来实际写代码。

---

## 七、定义配置数据结构：config_manager.h

首先新建 `src/config_manager.h`。这个头文件不需要包含 `nlohmann/json.hpp`，让其他模块在使用配置结构体时，不必直接依赖 JSON 库的类型。

```cpp
#pragma once

#include <filesystem>
#include <string>
#include <vector>

struct NoteConfig
{
    int number = 60;
    float velocity = 1.0f;
    float holdTime = 1.0f;
    float startTime = 0.0f;
};

struct ADSRConfig
{
    float attack = 0.05f;
    float decay = 0.3f;
    float sustain = 0.3f;
    float release = 1.5f;
};

struct TrackConfig
{
    std::string name;
    std::string wavetable = "sine";
    std::string curveType = "linear";
    ADSRConfig adsr;
    std::vector<NoteConfig> notes;
};

// 文件不存在时生成默认 JSON；存在时保留用户修改。
void EnsureDefaultConfig(const std::filesystem::path &path);

// 读取并验证每条音轨，最终返回普通 C++ 数据。
std::vector<TrackConfig> LoadTracks(const std::filesystem::path &path);
```

这里的 `NoteConfig` 对应每个音符的数据，`ADSRConfig` 对应音量包络，`TrackConfig` 则负责组织一条完整音轨。

有一个值得留意的小设计：**`TrackConfig` 暂时只保存波形与曲线的字符串，不直接保存 `OscillatorType` 和 `CurveType`。** 这意味着 `ConfigManager` 不需要依赖 `voice.h`，也不需要理解什么是振荡器；枚举转换可以在声音渲染模块完成。

不过这不意味着所有字符串都可以随意输入。在渲染时，我们仍然必须严格检查它们是不是合成器支持的类型。

## 八、把文件操作和解析统一交给 config_manager.cpp

新建 `src/config_manager.cpp`，这是本章 JSON 库真正发挥作用的地方。

下面的代码保留第五章使用的字段名称，支持多个顶层音轨，并且在第一次运行时创建默认配置。为方便阅读，我们将部分数据校验集中在一个函数里。

```cpp
#include "config_manager.h"

#include <nlohmann/json.hpp>

#include <cmath>
#include <fstream>
#include <stdexcept>
#include <string>
#include <vector>

using json = nlohmann::json;

namespace
{
json MakeDefaultJson()
{
    return {
        {"poly_chord", {
            {"note", {
                {"noteNumber", {60, 64, 67}},
                {"noteVelocity", {0.8, 0.7, 0.6}},
                {"holdTimes", {3.0, 3.0, 3.0}},
                {"startTime", {0.0, 0.0, 0.0}}
            }},
            {"ADSR_config", {0.05, 0.3, 0.3, 1.5}},
            {"wavetable", "sawtooth"},
            {"curveType", "linear"}
        }},
        {"poly_arpeggio", {
            {"note", {
                {"noteNumber", {60, 64, 67, 72}},
                {"noteVelocity", {0.8, 0.7, 0.6, 0.5}},
                {"holdTimes", {2.0, 2.0, 2.0, 2.0}},
                {"startTime", {0.0, 0.8, 1.6, 2.4}}
            }},
            {"ADSR_config", {0.05, 0.3, 0.3, 1.5}},
            {"wavetable", "sine"},
            {"curveType", "linear"}
        }}
    };
}

void ValidateTrack(const TrackConfig &track)
{
    if (track.notes.empty())
        throw std::runtime_error("Track has no notes: " + track.name);

    auto validTime = [](float value) {
        return std::isfinite(value) && value >= 0.0f;
    };

    if (!validTime(track.adsr.attack) ||
        !validTime(track.adsr.decay) ||
        !validTime(track.adsr.release) ||
        !std::isfinite(track.adsr.sustain) ||
        track.adsr.sustain < 0.0f || track.adsr.sustain > 1.0f)
    {
        throw std::runtime_error("Invalid ADSR in track: " + track.name);
    }

    // 输出文件名来自音轨名，禁止路径分隔符等危险字符。
    if (track.name.empty() ||
        track.name.find_first_not_of(
            "abcdefghijklmnopqrstuvwxyz"
            "ABCDEFGHIJKLMNOPQRSTUVWXYZ"
            "0123456789_-") != std::string::npos)
    {
        throw std::runtime_error("Invalid track name: " + track.name);
    }

    for (const auto &note : track.notes)
    {
        if (note.number < 0 || note.number > 127 ||
            !std::isfinite(note.velocity) ||
            note.velocity < 0.0f || note.velocity > 1.0f ||
            !validTime(note.holdTime) ||
            !validTime(note.startTime))
        {
            throw std::runtime_error("Invalid note in track: " + track.name);
        }
    }
}

TrackConfig ParseTrack(const std::string &name, const json &j)
{
    TrackConfig track;
    track.name = name;
    track.wavetable = j.at("wavetable").get<std::string>();
    track.curveType = j.at("curveType").get<std::string>();

    const auto &adsr = j.at("ADSR_config");
    if (!adsr.is_array() || adsr.size() != 4)
        throw std::runtime_error("ADSR_config needs 4 values: " + name);

    track.adsr = {
        adsr.at(0).get<float>(),
        adsr.at(1).get<float>(),
        adsr.at(2).get<float>(),
        adsr.at(3).get<float>()
    };

    const auto &n = j.at("note");

    const auto numbers = n.at("noteNumber").get<std::vector<int>>();
    const auto velocities = n.at("noteVelocity").get<std::vector<float>>();
    const auto holds = n.at("holdTimes").get<std::vector<float>>();
    const auto starts = n.at("startTime").get<std::vector<float>>();

    if (numbers.size() != velocities.size() ||
        numbers.size() != holds.size() ||
        numbers.size() != starts.size())
    {
        throw std::runtime_error("Note array size mismatch: " + name);
    }

    track.notes.reserve(numbers.size());
    for (size_t i = 0; i < numbers.size(); ++i)
    {
        track.notes.push_back({
            numbers[i], velocities[i], holds[i], starts[i]
        });
    }

    ValidateTrack(track);
    return track;
}
} // namespace

void EnsureDefaultConfig(const std::filesystem::path &path)
{
    if (std::filesystem::exists(path))
        return;

    if (!path.parent_path().empty())
        std::filesystem::create_directories(path.parent_path());

    std::ofstream output(path);
    if (!output)
        throw std::runtime_error("Cannot create JSON: " + path.string());

    output << MakeDefaultJson().dump(4) << '\n';
    if (!output)
        throw std::runtime_error("Cannot write JSON: " + path.string());
}

std::vector<TrackConfig> LoadTracks(const std::filesystem::path &path)
{
    std::ifstream input(path);
    if (!input)
        throw std::runtime_error("Cannot open JSON: " + path.string());

    json root;
    input >> root;

    if (!root.is_object() || root.empty())
        throw std::runtime_error("JSON root must be a nonempty object");

    std::vector<TrackConfig> tracks;
    tracks.reserve(root.size());

    for (auto it = root.begin(); it != root.end(); ++it)
    {
        tracks.push_back(ParseTrack(it.key(), it.value()));
    }

    return tracks;
}
```

这份实现里有几个值得重点理解的地方。

### 8.1 默认文件只在不存在时创建

```cpp
if (std::filesystem::exists(path))
    return;
```

这句看似普通，却是配置系统最重要的保护措施之一。否则每次运行程序都将 `config.json` 重写成默认内容，用户好不容易调出来的声音，下一次运行就全部消失了。

如果文件已存在但内容损坏，我们也不应该悄悄覆盖它，而是让解析阶段报错，提醒用户检查或备份配置。

### 8.2 读取整个文件，不需要写死音轨名

```cpp
for (auto it = root.begin(); it != root.end(); ++it)
{
    tracks.push_back(ParseTrack(it.key(), it.value()));
}
```

`it.key()` 是顶层音轨名，`it.value()` 是这条音轨对应的配置对象。因此不论文件里有 `poly_chord`、`poly_arpeggio`，还是新加的 `poly_melody`，都会进入相同的解析函数。

这里需要补充一个小细节：默认 `nlohmann::json` 的对象键通常按键名排序，不保证保留文本中书写的顺序。但本章每条音轨独立导出 WAV，因此处理顺序并不影响音频结果。如果将来要构建真正的按轨道排列的 DAW 工程，最好在 JSON 中明确使用数组表示轨道顺序。

### 8.3 每新增一个音符，C++ 自动增加一个 NoteConfig

```cpp
for (size_t i = 0; i < numbers.size(); ++i)
{
    track.notes.push_back({
        numbers[i], velocities[i], holds[i], starts[i]
    });
}
```

这里终于轮到 `push_back()` 正式上场了。注意，现在调用它的是 C++ 的 `std::vector<NoteConfig>`，而不是 JSON 中已经存在的音符数组。它负责把**解析后的音符**逐个加入配置结构体。

不过当前 JSON 使用了四个平行数组，这样写的代价就是必须检查长度。未来我们也可以考虑把结构改为 `"notes": [{"number": 60, "velocity": 0.8, ...}]`，将每个音符的数据放在一个对象里，避免四个数组彼此错位。本章为了兼容第五章的现有文件，暂时不做这次迁移。

## 九、只让声音渲染模块接触 Voice 和 PolySynth

我们已经成功把 JSON 解析成了 `TrackConfig`。下一步是将数据交给合成器，让它生成声音。

新建 `src/synth_renderer.h`：


然后新建 `src/synth_renderer.cpp`：

```cpp
#include "synth_renderer.h"

#include "voice.h"
#include "poly_synth.h"

#include <stdexcept>
#include <string>
#include <vector>

namespace
{
OscillatorType ParseWavetable(const std::string &name)
{
    if (name == "sine")
        return OscillatorType::Sine;
    if (name == "square")
        return OscillatorType::Square;
    if (name == "sawtooth")
        return OscillatorType::Sawtooth;
    if (name == "triangle")
        return OscillatorType::Triangle;

    throw std::invalid_argument("Unknown wavetable: " + name);
}

CurveType ParseCurveType(const std::string &name)
{
    if (name == "linear")
        return CurveType::Linear;
    if (name == "EaseIn")
        return CurveType::EaseIn;
    if (name == "EaseOut")
        return CurveType::EaseOut;

    throw std::invalid_argument("Unknown curve type: " + name);
}

void ConfigureVoice(
    Voice &voice,
    const TrackConfig &track,
    double sampleRate)
{
    voice.setSampleRate(sampleRate);
    voice.setWavetable(ParseWavetable(track.wavetable));
    voice.setCurveType(ParseCurveType(track.curveType));

    voice.setADSRAll(
        track.adsr.attack,
        track.adsr.decay,
        track.adsr.sustain,
        track.adsr.release
    );
}
} // namespace

std::vector<float> RenderTrack(
    const TrackConfig &track,
    double sampleRate)
{
    // 本章仍采用第五章的“一音符对应一 Voice”离线方案。
    std::vector<Voice> voices(track.notes.size());
    PolySynth synth;

    // 提前统一配置，再注册 Voice 指针。
    // 注册后不要让 voices 扩容，以免旧指针失效。
    for (auto &voice : voices)
    {
        ConfigureVoice(voice, track, sampleRate);
        synth.addVoice(&voice);
    }

    std::vector<int> noteNums;
    std::vector<float> velocities;
    std::vector<float> holdTimes;
    std::vector<float> startTimes;

    const auto count = track.notes.size();
    noteNums.reserve(count);
    velocities.reserve(count);
    holdTimes.reserve(count);
    startTimes.reserve(count);

    for (const auto &note : track.notes)
    {
        noteNums.push_back(note.number);
        velocities.push_back(note.velocity);
        holdTimes.push_back(note.holdTime);
        startTimes.push_back(note.startTime);
    }

    // 与第五章教程保持一致：四参数 generate。
    return synth.generate(
        noteNums,
        velocities,
        holdTimes,
        startTimes
    );
}
```

这里有三个关键设计。

第一，`ParseWavetable()` 和 `ParseCurveType()` 位于渲染模块，而不是 `ConfigManager`。前者处理外部字符串如何映射到 **DSP 类型**，后者只管外部文件如何变成结构化数据。字符串 `"sine"` 并不能直接传给需要 `OscillatorType` 的 `setWavetable()`，所以转换函数不可少。

第二，**所有声音参数终于真正来自 JSON**：

```cpp
voice.setWavetable(ParseWavetable(track.wavetable));
voice.setCurveType(ParseCurveType(track.curveType));
voice.setADSRAll(
    track.adsr.attack,
    track.adsr.decay,
    track.adsr.sustain,
    track.adsr.release
);
```

这跟以前直接写死 `Sawtooth` 和 `Linear` 已经有本质区别。

第三，我们保留第五章的四参数 `generate(noteNums, velocities, holdTimes, startTimes)`，**真正把 JSON 里的 startTime 交给 PolySynth**。如果你的本地 `poly_synth.h` 仍然只有三参数版本，那么必须先按第五章加入起音时间支持，不能仅仅传入一个 `startTimes` 数组就指望程序自动变成琶音。

> **关于曲线接口的范围：** 前面的非线性 ADSR 章节介绍过每个阶段的 `strength` 和曲率函数；但本章沿用你当前展示的 `Voice::setCurveType()` 统一曲线接口，不假设已经存在 `setCurveStrength()` 等方法。因此 JSON 在本章只负责切换当前实现允许的 `linear`、`EaseIn`、`EaseOut`，并不独立设置 Attack/Decay/Release 三段曲线。真实效果仍以现有 `Voice` / `EnvelopeADSR` 实现为准。

## 十、把 main() 缩减成一张流程表

现在我们已经把 JSON 读取放进了 ConfigManager，把 Voice 初始化与声音合成放进了 SynthRenderer。`main()` 终于不需要知道 JSON 内部有多少层中括号，也不需要区分当前合成的是和弦还是琶音。

只要保留前面 WAV 篇已经实现的写入函数，我们就可以这样调度：

```cpp
#include "config_manager.h"
#include "synth_renderer.h"
#include "wav_and_pcm.h"

#include <algorithm>
#include <cmath>
#include <cstdint>
#include <filesystem>
#include <fstream>
#include <iostream>
#include <limits>
#include <stdexcept>
#include <vector>

// 本章复用前面章节的 WAV Header / 小端写入工具。
// 这里输入 buffer 为单声道 Float PCM，再复制到 L/R 两个声道。
void GenerateWavFile(
    const std::filesystem::path &path,
    const std::vector<float> &buffer,
    double sampleRate)
{
    constexpr int channels = 2;

    // 经典 PCM WAV 使用 32-bit chunk 大小，限制数据长度。
    if (buffer.size() >
        (std::numeric_limits<uint32_t>::max() - 36u) / (channels * 2u))
    {
        throw std::runtime_error("WAV is too large");
    }

    const auto frames = static_cast<uint32_t>(buffer.size());
    std::ofstream out(path, std::ios::binary);
    if (!out)
        throw std::runtime_error("Cannot create WAV: " + path.string());

    WriteWavHeader(out, sampleRate, channels, frames);

    float peak = 0.0f;
    for (float value : buffer)
    {
        if (!std::isfinite(value))
            throw std::runtime_error("Non-finite sample in audio buffer");
        peak = std::max(peak, std::abs(value));
    }

    const float gain = peak > 1.0f ? 1.0f / peak : 1.0f;

    for (float value : buffer)
    {
        const long scaled = std::lround(value * gain * 32767.0f);
        const int16_t sample = static_cast<int16_t>(
            std::clamp(scaled, -32768L, 32767L)
        );

        for (int ch = 0; ch < channels; ++ch)
            WriteU16LE(out, static_cast<uint16_t>(sample));
    }

    if (!out)
        throw std::runtime_error("Failed to write WAV: " + path.string());
}

int main()
{
    try
    {
        constexpr double sampleRate = 44100.0;
        const std::filesystem::path configPath = "config/config.json";
        const std::filesystem::path outputDir = "output";

        EnsureDefaultConfig(configPath);
        const auto tracks = LoadTracks(configPath);

        std::filesystem::create_directories(outputDir);

        for (const auto &track : tracks)
        {
            const auto buffer = RenderTrack(track, sampleRate);
            const auto outputPath = outputDir / (track.name + ".wav");

            GenerateWavFile(outputPath, buffer, sampleRate);
            std::cout << "Done: " << outputPath.string() << '\n';
        }
    }
    catch (const std::exception &e)
    {
        std::cerr << "Error: " << e.what() << '\n';
        return 1;
    }

    return 0;
}
```

**这里有一个边界要说清楚：** 上述 WAV 代码使用你在第一章实现的 `WriteWavHeader(out, sampleRate, channels, frames)` 和 `WriteU16LE(out, value)`。如果你的本地函数签名与教程不同，需要按照本地 `wav_and_pcm.h` 调整调用。其余新模块的接口在本文中均已给出。

为什么这里的 `sampleRate` 仍然放在 C++ 中？因为本章主要把**音色预设与音符事件**外置，采样率先作为离线渲染器的统一系统设置保留。以后可以进一步把它放进全局工程配置，但要同时确保 Voice、PolySynth、WAV Header 使用相同的采样率，不能只改一个位置。

## 十一、实验：不改 C++，做三种不同的声音

现在我们有了一套比较清楚的配置流程，终于可以做声音实验了。请先成功编译一次程序，然后只改 `config/config.json`，保存后重新运行可执行文件。

### 实验 A：更改振荡器波形

把 `poly_chord` 中的：

```json
"wavetable": "sawtooth"
```

改成：

```json
"wavetable": "sine"
```

对于同样的音符组合，正弦波通常更单纯，锯齿波则拥有更多谐波，高频成分更丰富。我们在第二章已经从傅里叶级数讨论过二者差异，这次不需要重新修改 `Oscillator` 类，就能直观地比较这些声音。

### 实验 B：改变 ADSR 包络

原本：

```json
"ADSR_config": [0.05, 0.3, 0.3, 1.5]
```

修改为：

```json
"ADSR_config": [0.8, 0.3, 0.6, 2.0]
```

Attack 由 0.05 秒变为 0.8 秒，起音更慢；Sustain Level 提高到 0.6；Release 延长到 2.0 秒，NoteOff 之后的收尾时间也会增长。

这里我们并没有改变 ADSR 的状态机。第三章仍然负责回答“当前处于哪个阶段”，第四章仍然负责计算“阶段中的进度如何映射到音量”，JSON 只是把相关参数从外部送入这个系统。

### 实验 C：和弦变琶音

只需要把原本同时起音的：

```json
"startTime": [0.0, 0.0, 0.0]
```

修改成：

```json
"startTime": [0.0, 0.5, 1.0]
```

此时 C4、E4、G4 将在不同时间触发。如果采样率是 44100 Hz，那么 0.5 秒对应 22050 个 Sample Frame，1.0 秒对应 44100 个 Sample Frame。这正是第五章解释过的：

$$
N = t f_s
$$

不同 Voice 仍在同一条全局 Sample 时间轴上运行，只是 NoteOn 发生在不同位置。因此，这里配置的不只是“声音参数”，也开始涉及简单的**事件时间编排**。未来读取 MIDI 文件时，这套思想还能继续使用。

### 如何判断“无需重新编译”真的实现了？

先构建一次：

```bash
cmake --build cmake-build
```

之后每次修改 `config.json`，只重新运行现有可执行程序即可：

```bash
./cmake-build/mini_audio_demo.exe
```

不需要再运行 `cmake --build`。如果你改的是 `Voice` 或 `PolySynth` 的 C++ 实现，那仍然需要重新编译，这两种情况务必分开。

## 十二、从“能运行”到“容易维护”：我们究竟降低了什么耦合？

在软件工程中，经常听到一个词：**Coupling（耦合）**。它描述了不同模块彼此依赖的程度。耦合并不是越少越抽象、越分文件越高级，而是看修改一个地方时，会不会无缘无故牵连许多其他模块。

旧版程序的关系大致是：

```text
main.cpp
├── 了解 JSON 的键名
├── 了解音符数组的长度
├── 了解 OscillatorType 的具体枚举
├── 了解 ADSR 的四个参数
├── 了解 PolySynth::generate()
└── 了解 WAV 写入
```

新版程序则变成：

```text
main.cpp
  ├── EnsureDefaultConfig() / LoadTracks()
  ├── RenderTrack()
  └── GenerateWavFile()

config_manager.cpp
  ├── nlohmann/json
  ├── 文件 I/O
  └── 数据校验 / JSON -> TrackConfig

synth_renderer.cpp
  ├── TrackConfig -> DSP 枚举
  ├── ConfigureVoice()
  └── PolySynth::generate()

Voice / PolySynth / Envelope / Oscillator
  └── 只负责声音行为，不负责 JSON 文件格式
```

未来即使我们把文件格式换成 TOML、YAML，或者从 GUI 表单中直接构造 `TrackConfig`，理论上也不必改动 `Voice::process()` 里每个 Sample 的计算逻辑。当然，前提是外部数据最终仍能转换成相同的配置结构体。

这里还能联想到第二章讲过的封装：当时我强调 `Oscillator` 的 `phase` 必须保持为内部状态，不应该让外部随意修改。现在的道理其实一样。**外部只应该告诉合成器“我要什么声音”，而不应该直接操纵每个采样点的内部状态。**

但是，`TrackConfig` 也不是最终的通用参数系统。对于真正成熟的合成器，我们可能还需要参数范围、默认值、预设版本、平滑更新以及 Automation。第 5.5 章只是搭建数据入口，为未来的实时音频工程准备一个清晰的起点。

## 十三、常见报错与排查

### 13.1 `nlohmann_jsonConfig.cmake` 找不到

先检查 UCRT64 包是否真的安装：

```bash
pacman -Q mingw-w64-ucrt-x86_64-nlohmann-json
ls /ucrt64/share/cmake/nlohmann_json/
```

确认 CMake 与编译器来自同一套 UCRT64 工具链，并使用**新的构建目录**重新配置：

```bash
cmake -S . -B cmake-build-ucrt -G Ninja -DCMAKE_PREFIX_PATH=/ucrt64
```

不要误以为之前通过 vcpkg 安装过 `nlohmann-json:x64-windows`，UCRT64 的 CMake 就一定能直接使用它。MSVC 对应的 `x64-windows` 与 MinGW/UCRT64 属于不同工具链环境。

### 13.2 CMake 停在编译器检测之后

`Detecting CXX compile features - done` 只表示编译器检测通过，不意味着后面的配置阶段已经成功。使用 `--trace-source`、`--debug-find-pkg` 观察实际执行进度，并检查 CMakeLists 中的其他依赖及自定义步骤。

### 13.3 `JSON parse error`

常见原因是少了逗号、字符串没加双引号，或者插入了 `//` 注释。JSON 文件是数据，不是 C++ 源码。

### 13.4 `key 'ADSR_config' not found`

`at()` 会在找不到键时抛出异常，这是刻意的选择。与其错误配置悄悄生效，不如明确知道哪一项缺失。检查键名大小写和层级结构。

### 13.5 `Unknown wavetable: supersaw`

配置文件不能自动创造 `OscillatorType::Supersaw`。如果你真的实现了新的波形，需要同步扩展 C++ 的枚举和 `ParseWavetable()` 映射，然后重新编译一次。之后才能直接通过 JSON 切换它。

### 13.6 改了 JSON，但输出听起来没变化

先检查程序读的到底是不是你修改的那一份文件，尤其留意 `config.json` 与 `config/config.json`。再检查是否只是反复播放旧的 WAV，以及是否在程序启动后才改文件。本章只在**启动时**读取配置。

### 13.7 `std::vector<Voice>` 编译失败

本章示例假设当前 `Voice` 类型允许默认构造。如果你的本地 `Voice` 必须通过带参构造函数创建，可以改用 `std::vector<std::unique_ptr<Voice>>` 等方案持有 Voice，随后向 `PolySynth` 注册 `voice.get()`，但必须保证 Voice 在渲染期间一直存活。

## 附录 A：如果使用 vcpkg + MSVC

本章正文已经使用 MSYS2 UCRT64 安装依赖。如果你在另一台 Windows 电脑上使用 Visual Studio / MSVC，也可以让 vcpkg 负责 JSON 库。

在项目根目录中，第一次启用 Manifest Mode 时可以使用：

```powershell
vcpkg new --application
vcpkg add port nlohmann-json
vcpkg install --triplet x64-windows
```

对应 `vcpkg.json` 至少应包含：

```json
{
    "dependencies": [
        "nlohmann-json"
    ]
}
```

上面是说明依赖的最小结构；如果 `vcpkg new` 为你生成了其他配置或基线信息，请保留它，不必为了模仿这段代码而删除。

然后给 CMake 指定 vcpkg 工具链。假设 `VCPKG_ROOT` 已设置为实际的 vcpkg 安装根目录：

```powershell
$toolchain = Join-Path $env:VCPKG_ROOT "scripts/buildsystems/vcpkg.cmake"

cmake -S . -B build-msvc `
  -G "Visual Studio 17 2022" -A x64 `
  -DCMAKE_TOOLCHAIN_FILE="$toolchain" `
  -DVCPKG_TARGET_TRIPLET=x64-windows

cmake --build build-msvc --config Debug
```

此处生成器与 Visual Studio 版本只是示例，请根据实际安装版本调整。一个常见误区是：**MSYS2 UCRT64 正在用 GCC 编译，却把 vcpkg 中的 `x64-windows` MSVC 依赖当作当前 MinGW 工程的通用安装包。** 一般不应随意混用这两套工具链。本章推荐根据项目最终使用的编译器选择一种主依赖管理路线。

另一个误区是认为 vcpkg 安装 JSON 库本身必然依赖 PowerShell 7。`nlohmann/json` 是纯头文件库，下载 PowerShell 可能只是 vcpkg 工具链在该安装流程中需要的辅助步骤，并非 JSON 解析器运行时的依赖。

## 附录 B：今后还可以怎么扩展？

现在的 `config.json` 已经能描述音符、振荡器波形、包络参数和统一曲线类型。下一阶段可以逐步扩展以下几个方面：

1. **Preset**：将不同音色保存为独立的配置文件，例如 `soft_pad.json` 和 `pluck.json`。
2. **音符对象数组**：将当前四组平行数组改成每个音符一个对象，减少数据错位风险。
3. **配置版本号**：以后修改 JSON 结构时，能够识别老版本并进行迁移。
4. **GUI 参数编辑器**：允许用户拖动滑块再保存配置，而不是手动编辑 JSON。
5. **实时参数更新**：通过安全的控制消息和参数平滑机制，将修改送入音频线程，而不是让音频回调直接进行文件读取与 JSON 解析。

这里最后一项尤其重要。我们现在做的是**离线音频渲染**：程序有充足时间读取 JSON、分配内存并生成 WAV。但在真正的低延迟实时音频系统中，不应该把文件 I/O、JSON 解析和不受控的动态分配放进每次处理音频的回调里。等到实时音频章节，我们再专门解释为什么。

## 结语：从“能够合成声音”到“能够配置声音”

第一章，我们让 C++ 将一串数字写成 WAV 文件；第二章，我们用 Oscillator 和傅里叶级数创造音色；第三、四章，我们为声音赋予 ADSR 的生命周期；第五章，我们用 PolySynth 让多个 Voice 共同演奏。

而这一章，并没有让我们的合成器多出什么惊天动地的新算法。声音依然经过同样的计算过程：

```text
Note -> Voice -> Oscillator / ADSR -> PolySynth -> Float Buffer -> PCM -> WAV
```

真正改变的是声音的**控制方式**：

```text
以前：修改 C++ 参数 -> 编译 -> 运行 -> WAV

现在：修改 JSON 参数 -> 运行已有程序 -> WAV
```

这两条流程看起来只差了一个“重新编译”，但在软件工程里，它意味着**用户配置与算法实现第一次真正分离**。我们终于可以像调合成器预设那样修改参数，不必每次都拆开软件内部电路。

而且还有一个长期好处：当我们未来实现 Filter、LFO、MIDI，甚至 VST3 插件时，只要这些新模块也能够接收明确的数据结构，就有机会沿着同一条配置与参数管理路线继续扩展。

下一章，我们回到 DSP 本身，开始尝试用低通、高通以及后续的 Biquad Filter 进一步塑造音色。到时候，`cutoff`、`resonance` 和 `filterType` 也很适合加入同一套配置体系。

**这一期我们的收获，不只是学会读取一个 JSON 文件，而是让一台只会执行固定指令的合成器，开始拥有可编辑、可保存的声音配置。**
